# 이미지 표시 지연 분석 — 2026-11-05

## 확인한 결과

운영 사이트 `https://kanjimanabo.com/kanji/#kanji=%E6%96%87`를 새 Chrome 컨텍스트에서 열어 실제 외부 이미지 요청을 측정했다. 브라우저 캐시가 없는 단일 표본이며 네트워크 제한은 설정하지 않았다. 아래 시간은 사용자 전체의 평균이나 최악 시간을 뜻하지 않는다.

## 원인

1. **클릭 후에야 다운로드 시작.** `src/main.js:1227`의 `setCardFlipped`가 처음 뒤집을 때 `data-src`를 `src`로 옮긴다. 초기 96개 카드를 렌더링할 때 이미지 요청이 0개인 것은 기존 브라우저 테스트로도 확인했다. 초기 페이지 부담은 줄지만 처음 뒤집을 때 네트워크 대기 시간이 그대로 드러난다.
2. **이미지 크기가 용도별로 나뉘지 않음.** `src/image-sources.js:33`은 카드·상세·확대·획순 모두 `w1200`을 사용한다. 암기 이미지 2,324개와 획순 2,324개 모두 Drive 주소다. 文 외에 学도 요청 결과 약 1.46MB였다. 전체 이미지의 평균 용량은 조사하지 않았다.
3. **Drive를 거쳐 이미지 서버로 이동.** 첫 URL은 `drive.google.com/thumbnail`, 실제 이미지 응답은 `lh3.googleusercontent.com/d/…=w1200`이다. 文에서는 이 이동까지 약 452ms가 들었다. Drive의 302 응답은 `no-cache, no-store`이며 최종 이미지 응답은 `private, max-age=86400`이었다. 최종 이미지에는 브라우저 캐시가 있으므로 “캐시가 전혀 없다”는 진단은 잘못이다.
4. **느린 응답은 대체 URL로 전환되지 않음.** 현재 fallback은 `error` 이벤트에만 반응하고 별도 시간 제한이 없다. 첫 요청이 실패하지 않고 느리게 끝나면 계속 기다린다. 이번 표본에서는 HTTP 오류 없이 모두 성공했으므로 오류 재시도가 관측된 병목은 아니다.

상세 이미지에도 `loading="lazy"`가 있지만 이번 표본에서는 화면이 열린 직후 요청이 시작됐다. 이것을 수초 지연의 주원인으로 단정할 근거는 없다. JSON과 화면 준비 시간보다 이미지 요청 체인의 시간이 더 길었다.

## 개선 우선순위

1. 카드에는 표시 크기와 화면 배율에 맞는 작은 이미지를, 상세·확대에는 큰 이미지를 제공한다. 예를 들어 카드용 480px부터 비교하되 고해상도 화면의 선명도를 확인해야 한다. [Chrome의 반응형 이미지 가이드](https://web.dev/articles/serve-responsive-images)
2. 화면에 보이는 카드나 사용자가 포인터·키보드로 선택한 카드만 제한적으로 미리 요청한다. 96개 전체를 한꺼번에 다운로드하면 초기 로딩 부담이 다시 늘어난다. 상세 대표 이미지는 즉시 요청하고 화면 아래의 획순은 지연 로딩을 유지하는 방식을 검토한다. [Chrome의 이미지 지연 로딩 가이드](https://web.dev/articles/browser-level-image-lazy-loading)
3. 단기적으로 직접 이미지 URL을 먼저 요청하면 이번 표본의 Drive 리다이렉트를 줄일 수 있다. 기존 fallback과 다른 한자의 접근 성공 여부를 확인한 뒤 바꿔야 하며, 단일 성공 사례가 전체 파일의 장기 가용성을 보장하지는 않는다.
4. 안정적인 개선은 배포 시 최적화한 이미지 파일을 사이트 정적 자산이나 전용 이미지 저장소에서 제공하는 방식이다. 파일 버전별 URL과 캐시 정책을 함께 관리하면 Drive 왕복 의존성을 줄일 수 있다. 실제 이전이나 이미지 변환은 이번 분석에서 수행하지 않았다.
