## 검사 범위와 제한

형식 검사는 JSON 값의 공백 제거 후 표준 URL 파싱 가능 여부, `http:` 또는 `https:` 프로토콜 여부, 호스트 존재 여부, Google Drive `/file/d/{파일 ID}` 패턴을 기준으로 했다.

이번 작업에서는 보호 조건에 따라 이미지 URL로 네트워크 요청을 보내지 않았다. 따라서 다음 항목은 아직 확인하지 않았다.

- 파일의 실제 존재 여부와 공유 권한
- 리디렉션 후 최종 주소 및 응답 상태
- 실제 MIME 유형과 손상 여부
- 파일별 용량, 전체 저장 용량 및 해상도
- 서로 다른 URL이 같은 이미지 내용을 가리키는 내용 기반 중복

행 단위 결과는 [`image-inventory.csv`](./image-inventory.csv)에 정리했다.

## 저장 방식 비교

### `public/images`에 직접 저장

장점:

- 별도 저장소 계정이나 API가 필요 없어 구조가 가장 단순하다.
- 이미지와 코드 변경을 같은 배포 단위로 관리할 수 있다.
- Vite는 `public`의 파일을 개발 서버 루트에서 제공하고 빌드 결과에 그대로 복사한다. [Vite 정적 자산 문서](https://vite.dev/guide/assets.html#the-public-directory)

단점:

- 4,648개 파일이 저장소와 모든 빌드·배포 산출물에 포함된다.
- 이미지 변경마다 웹사이트 전체를 다시 배포해야 한다.
- 총 파일 크기를 아직 알 수 없어 Git 저장소 및 호스팅 배포 제한에 들어오는지 판단할 수 없다.
- 원본 파일명 유지 방식에서는 콘텐츠 해시 기반 캐시 갱신을 별도로 설계해야 한다.

적합한 경우: 전체 용량이 작고 이미지 변경이 드물며, 운영 단순성이 최우선일 때.

### Supabase Storage

장점:

- 파일용 버킷, 직접 URL, 세밀한 접근 제어, S3 호환 접근, CDN과 이미지 변환 기능을 함께 제공한다. [Supabase Storage 문서](https://supabase.com/docs/guides/storage)
- 향후 관리자 업로드 화면이나 권한 관리가 필요해질 경우 확장하기 쉽다.

단점:

- 정적 공개 이미지에 필요하지 않은 데이터베이스 프로젝트 운영 요소가 함께 생긴다.
- 무료 플랜은 파일 저장소 1GB, 캐시 및 일반 egress 각각 5GB가 포함되며, 무료 프로젝트는 비활성 시 일시 중지될 수 있다. 트래픽이 커지면 egress를 관리해야 한다. [Supabase 요금 문서](https://supabase.com/pricing)
- 현재 요구사항에는 인증이나 행 단위 권한이 없어 주요 장점이 충분히 활용되지 않는다.

적합한 경우: 이미지 외에도 관리자 UI, 인증, 데이터베이스와 통합된 권한 관리가 필요할 때.

### Cloudflare R2

장점:

- S3 호환 객체 저장소이며 CLI와 API로 대량 파일을 관리할 수 있다. [R2 시작 문서](https://developers.cloudflare.com/r2/get-started/)
- 인터넷 전송 egress 요금이 없고, Standard 클래스의 월 무료 구간은 저장 10GB, Class A 작업 100만 건, Class B 작업 1,000만 건이다. [R2 요금 문서](https://developers.cloudflare.com/r2/pricing/)
- 4,648개의 공개 정적 이미지를 코드 저장소와 분리하면서 트래픽 증가에 대응하기 좋다.

단점:

- 버킷, 공개 도메인, 캐시 정책, CORS 및 업로드 도구를 별도로 설정해야 한다.
- 요청 작업량은 무료 구간 이후 과금되므로 실제 트래픽을 모니터링해야 한다.
- Supabase처럼 통합 관리자 UI나 이미지 변환 기능이 기본 업무 흐름으로 제공되는 것은 아니다.

적합한 경우: 공개 정적 파일이 많고 전송량 증가 가능성이 있으며, S3 방식의 운영이 가능한 경우.

## 제안

현재 자료에는 4,648개의 고유한 공개 이미지가 있고 모든 이미지가 외부 Google Drive에 의존한다. 총 용량은 아직 알 수 없지만 파일 개수만 보아도 저장소와 웹 배포물을 분리하는 편이 관리에 유리하다. 따라서 **Cloudflare R2를 우선 후보로 추천한다.** 공개 정적 자산이라는 용도와 무료 egress, S3 호환 대량 관리 방식이 현재 규모에 가장 잘 맞는다.

다만 실제 총 용량이 매우 작고 이미지 갱신이 거의 없다면 `public/images`가 운영 복잡도 면에서는 더 경제적일 수 있다. 다음 단계에서 파일 크기를 확인한 뒤 아래 기준으로 최종 결정한다.

- 전체 용량이 배포 플랫폼 한도보다 충분히 작고 변경이 드묾: `public/images`
- 관리자 권한·업로드 UI·Supabase 데이터 기능도 함께 필요함: Supabase Storage
- 공개 이미지의 독립 관리와 트래픽 확장성이 중요함: Cloudflare R2

2. 전체 바이트 용량과 파일 형식별 분포를 계산해 저장·전송 비용을 다시 추정한다.
3. `한자/이미지 종류`를 기반으로 충돌 없는 객체 키 규칙을 정한다.
4. URL, 객체 키, 체크섬, 업로드 상태를 담는 이전 매니페스트를 만든다.
5. 소규모 표본으로 후보 저장소의 표시 품질, 캐시, 권한과 장애 시 동작을 검증한다.
6. 전체 업로드 후 원본과 대상의 개수 및 체크섬을 대조한다.
7. 모든 검증이 끝난 뒤에만 JSON URL을 일괄 변경하고 되돌리기용 매핑을 보관한다.
