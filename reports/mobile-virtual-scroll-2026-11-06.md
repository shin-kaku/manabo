# 모바일 연속 스크롤 조사 및 가상 목록 적용

## 원인 조사

2026-11-06 운영 `/kanji/`를 Chrome 모바일 에뮬레이션(390×844, DPR 3)으로 조사했다.
카드를 뒤집지 않고 페이지 끝으로 이동하면서 기존 96개씩 추가하는 동작을 측정했다.

| 카드 수 | 목록 내부 요소 | CDP DOM 노드* | 이벤트 리스너* | GC 이후 JS heap |
| ---: | ---: | ---: | ---: | ---: |
| 96 | 1,916 | 4,580 | 927 | 3.73MiB |
| 480 | 9,958 | 20,805 | 4,758 | 4.89MiB |
| 960 | 20,074 | 41,258 | 9,594 | 5.54MiB |
| 1,536 | 32,275 | 66,030 | 15,459 | 6.11MiB |

*CDP 카운터는 페이지 전체를 포함한다. JS heap은 DOM/그래픽 자원 등 전체 프로세스 메모리를 뜻하지 않는다.

이 구간에서 한자 이미지 요청은 0건이었다. 목록은 지나간 카드를 제거하지 않았으며 모든 카드에
`perspective`, `preserve-3d`, `will-change: transform`이 적용됐다. 화면 요소와 이벤트가 계속
누적되는 구조는 확인했지만, 실물 휴대폰의 프로세스 종료나 GPU 메모리 부족 자체는 재현하지 못했다.
레이어 측정값은 얻지 못해 그래픽 메모리 사용량을 추정 수치로 제시하지 않는다.
조사 스크립트는 전체 2,324개를 예상했지만 기본 상용한자 필터는 2,136개라 마지막 대기에서
타임아웃됐으며, 위 표는 실제 출력된 중간 측정값만 기록했다.

메모리 부담은 기기별로 다르게 나타나므로 데스크톱 에뮬레이션 결과만으로 휴대폰 종료 원인을
확정할 수 없다. [Chrome 메모리 진단 가이드](https://developer.chrome.com/docs/devtools/memory-problems)
상시 `will-change`의 과도한 사용도 자원 사용을 늘릴 수 있다.
[MDN will-change 가이드](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/will-change)

## 참고한 오늘의집 구조

사용자 지정 [오늘의집 집사진 목록](https://ohou.se/contents/card_collections)의 공개 HTML에서
`virtualized-list`를, 페이지에 연결된 공개 `VirtualizedList-D3AnMpH0.js`에서
표시 구간(start/end), 주변 여유 영역(overscan), 빠른 스크롤 상태, resize/위치 보정,
requestAnimationFrame 기반 갱신을 확인했다. 브라우저 연결 도구는 이용 불가여서 오늘의집의
실제 터치 스크롤은 관찰하지 못했다. 해당 소스를 복제하거나 React 의존성을 추가하지 않고,
마나보의 고정 2:3 카드 비율과 기존 CSS 열 수에 맞춰 작은 모듈로 구현했다.

## 적용 내용

- `virtual-grid.js`: 전체 목록 높이는 유지하고 실제 화면 및 앞뒤 3개 행만 마운트한다.
  지나간 카드·이벤트·미완료 이미지는 해제한다. CSS의 2~6열 설정을 읽고 폭/회전 변경 시
  현재 보고 있던 항목 부근을 유지한다. 프레임당 갱신을 예약하며 포커스 중인 카드 1개는 보존한다.
- 키보드 Tab/Shift+Tab이 아직 렌더링되지 않은 다음/이전 카드로 향하면 해당 구간을 즉시 만든다.
  검색·정렬·필터 변경은 목록을 재설정하고, 상세보기 동안은 목록 갱신을 멈춘다.
- `card-images.js`: 카드 생성이나 주변 여유 영역만으로 이미지를 요청하지 않는다.
  화면에 실제로 보이는 뒤집힌 카드만 요청하고 스크롤 중에는 신규 요청을 보류한다.
  스크롤 정지 160ms 후 현재 화면의 필요한 이미지만 재개한다.
- 목록 이미지 동시 요청은 2개. 완료 이미지 요소는 최근 4개만 보관해 가까운 재방문에서
  Drive 재요청을 줄이며, 큰 이미지 전체를 무제한 메모리에 보관하지 않는다.
- 화면 밖 미완료 이미지의 `src`와 이벤트 핸들러를 해제하고 재시도 대기열에서도 제거한다.
  이미 전송된 네트워크 요청의 실제 취소 여부/시점은 브라우저 동작에 따른다.
- 상시 `will-change: transform`을 제거했다. 카드 뒤집기 및 기존 디자인은 유지한다.
  이전 요청의 루비 130% 확대도 보존했다.

## 변경 후 브라우저 측정

외부 이미지는 mock, 실제 한자 JSON은 로컬 개발 서버에서 읽었다. 스크롤 위치를
5% → 20% → 50% → 80% → 끝 → 30% → 맨 위로 이동했다. 높이는 844px이다.

| 화면 폭 | 관측된 최대 카드 수 | 최대 목록 요소 수 | 카드 이미지 요청 | 한자 JSON 요청 |
| ---: | ---: | ---: | ---: | ---: |
| 390px | 20 | 428 | 0 | 1 |
| 768px | 30 | 643 | 0 | 1 |
| 1280px | 50 | 1,068 | 0 | 1 |
| 1600px | 60 | 1,276 | 0 | 1 |

이는 위 화면 크기/이동 경로에서의 최대값이며 모든 화면 크기의 하드코딩된 상한은 아니다.
390px에서는 1,536개 시점의 기존 목록 32,275개 요소가 화면 위치에 따라 약 200~430개로 제한된다.
기기 종료 해결 여부는 운영 배포 후 해당 휴대폰의 실사용 확인이 필요하다.

## 검증 범위

가상 목록·반응형 재배치·이미지 재사용·스크롤 중 요청 억제·동시 요청 제한·검색 결과 복구·
키보드 경계 이동과 기존 상세보기/퀴즈/독해를 포함한 브라우저 검사 47개가 최종 통과했다.
단위 검사 38개, 최종 배포용 빌드 및 `git diff --check`도 통과했다.
모바일/데스크톱 스크린샷에서 기존 카드 배치와 가로 넘침이 없는 것을 확인했다.
초기 Chrome 작업자 1개가 페이지 생성 단계에서 멈춰 병렬 수를 2로 줄였다.
중간 전체 검사에서 확인한 빠른 Tab 경계 이동 실패는 수정하고 정방향/역방향을 재검증했다.
테스트와 배포용 빌드는 생성 HTML을 공유하므로 동시에 실행하지 않는다.
이번 변경은 로컬 소스 적용이며 커밋·푸시·운영 배포는 포함하지 않는다.
