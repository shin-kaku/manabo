# Manabo 오류 수정 및 안정화 작업 명세서

## 0. 작업 목표와 기준

이 문서에 따라 Manabo의 실제 코드를 수정하고, 회귀 테스트와 빌드 검증까지 완료하라. 분석이나 작업 계획만 제시하고 끝내지 말고, 검토 가능한 로컬 변경 사항을 남겨라.

- 저장소: https://github.com/shin-kaku/manabo
- 기본 브랜치: `master`
- 리뷰 기준 커밋: `3f5b575a40530fa6c6854fd4d8fe2ea9d7cdfdb2`
- 리뷰 기준일: 2026-10-19
- 현재 구조: Vite 기반 다중 페이지 정적 사이트, JavaScript, JSON 학습 데이터, Google Sheets 동기화 스크립트.

위 커밋은 문제를 확인한 기준점이다. 현재 브랜치나 HEAD가 달라졌다면 현재 코드에서 문제가 여전히 존재하는지 먼저 확인하고, 이미 해결된 항목은 중복 수정하지 마라. 리뷰 기준 커밋으로 강제 이동하거나 사용자의 변경 사항을 되돌리지 마라.

작업을 시작할 때 저장소의 `AGENTS.md` 등 적용되는 지침, 현재 브랜치, HEAD, `git status`를 확인하라. 사용자가 작성한 미커밋 변경 사항을 보존하고, 그 변경과 충돌하는 작업은 별도로 구분하라. 현재 코드와 이 문서의 파일 위치나 줄 번호가 다르면 실제 함수와 동작을 기준으로 찾아라.

## 2. 데이터 동기화 검증과 손실 방지

주요 파일:

- `scripts/sync-sheets.mjs`
- `scripts/sync-sheets.test.mjs`
- `public/data/kanji.json`
- `public/data/stories.json`

### 2-1. 한자 필수 필드 검증 누락 보완

현재 검증에서는 `발음`, `예시 단어`에 해당하는 실제 스키마 키 `예시단어`, `획순 이미지`가 전체 행에서 사라져도 동기화가 성공할 수 있다. 이 경우 화면의 해당 학습 정보가 조용히 사라진다.

다음 요구사항을 적용하라.

- 실제 데이터 스키마의 필드 이름을 사용하고, 키 누락과 잘못된 타입을 구분해 검증하라.
- 문자열 필드는 실제 문자열이어야 한다. 객체나 배열을 `String(value)`로 바꿔 유효한 텍스트로 인정하지 마라.
- 일반 학습 한자의 발음·예시단어·획순 이미지에는 현재 서비스가 요구하는 유효한 값이 있어야 한다.
- 이미지 URL은 기존 이미지 필드와 같은 수준으로 유효한 HTTP(S) URL인지 확인하라.
- 예시단어와 발음은 현재 데이터 형식 및 화면 파서가 읽을 수 있는 구조를 기준으로 검증하라. 이번 작업에서 언어 지식 전체를 판정하는 검증기를 만들지 마라.
- 현재 `참고` 항목에 의도적으로 비어 있는 예시단어 등이 존재한다. 실제 데이터 규칙을 확인해 필드별 예외를 좁게 정의하라.
- `참고`라는 이유로 해당 행의 모든 검증을 건너뛰지 마라.
- 정상적인 현재 데이터 전체는 계속 통과해야 한다.
- 오류에는 데이터 종류, 한자 또는 행 식별자, 필드, 실패 이유를 포함하라. 원문 전체를 출력할 필요는 없다.

### 2-2. 기존 행 수 보호와 숫자 식별자 정합성 유지

- 기존 한자 최소 행 수·급감 방지 정책을 보존하라.
- `암기순`은 유효한 양의 정수이고 중복되지 않아야 한다.
- 일반 학습 한자의 `문부성` 번호는 현재 데이터 규칙에 따라 유효하고 중복되지 않아야 한다.
- `참고` 항목에 적용되는 번호 예외를 보존하되, 일반 항목까지 예외로 취급하지 마라.
- 동일 번호를 여러 행에 넣은 응답을 거부하라.
- 검증 통과를 위해 데이터를 임의로 정렬하거나 번호를 다시 매기지 마라.
- 리뷰 당시 총 2,324자, 일반 2,136자, 참고 188자였다는 수치를 영구적인 상수로 박아 넣지 마라. 기존 정책·직전 정상 데이터·명시적인 데이터 규칙을 사용하라.

### 2-3. 읽기 데이터의 급감·삭제 보호

현재는 읽기 데이터가 19개에서 1개로 줄어도 동기화가 성공한다.

- 이전에 저장된 정상 `stories.json`의 개수와 ID를 읽고 새 응답과 비교하라.
- 기본 동작에서는 예기치 않은 항목 삭제나 대규모 감소를 거부하라.
- 총개수가 같더라도 기존 ID가 사라진 경우를 식별할 수 있어야 한다.
- 이전 파일이 존재하지만 손상되었거나 스키마가 잘못됐다면 이를 최초 동기화로 취급하지 말고 중단하라.
- 이전 파일이 없는 최초 생성은 별도 경로로 처리하고, 새 데이터에 대한 전체 스키마 검증을 수행하라.
- 실제로 읽기 항목 삭제가 필요한 경우를 위해 좁고 명시적인 절차를 문서화하라. 예를 들어 삭제할 ID를 명시적으로 확인하는 방식은 허용한다.
- 모든 검증을 끄는 범용 `--force`나 광범위한 우회 옵션으로 해결하지 마라.

### 2-4. 읽기 데이터 스키마 강화

- 실제 화면에서 사용하는 필드를 확인하고, ID·분류·학년/등급·버전·제목·본문 등에 적절한 타입 검증을 적용하라.
- 문자열이어야 하는 값이 객체·배열·숫자 등일 경우 거부하라.
- `String({})` 결과인 `[object Object]`를 본문으로 받아들이지 마라.
- 분류는 실제 내비게이션이 지원하는 값만 허용하라. 분류 오타 때문에 저장된 글이 목록에서 사라지지 않도록 하라.
- 학년·JLPT 등급 표기는 현재 데이터와 화면에서 지원하는 규칙에 맞는지 확인하라.
- 버전 배열이 비어 있거나 각 버전 구조가 유효하지 않으면 거부하라.
- ID 중복 검증을 유지하고, ID의 정규화가 필요하다면 비교와 저장 규칙이 서로 어긋나지 않게 하라.
- 정상적인 현재 읽기 데이터는 계속 통과해야 한다.

### 2-5. 두 파일의 일관된 교체

- 한자와 읽기 응답을 모두 검증한 뒤 파일 교체를 시작하라.
- 하나라도 검증에 실패하면 기존 `kanji.json`과 `stories.json`을 모두 그대로 보존하라.
- 실패 후 한 파일만 새 버전으로 남아서는 안 된다.
- 기존 임시 파일·백업·rollback 흐름을 확인하고, 필요한 범위에서 보완하라.
- 검증 실패와 쓰기 실패를 구분할 수 있는 오류를 남겨라.
- 실패 테스트에서는 두 파일의 내용을 바이트 단위로 비교해 변경되지 않았음을 확인하라.

## 3. 페이지별 데이터 로딩과 오류 복구

주요 파일: `src/main.js`, `src/study.html`, 필요한 범위의 `src/styles.css`.

### 3-1. 독립적인 데이터 의존성

현재 한자와 읽기 JSON을 하나의 `Promise.all`로 처리해 읽기 데이터 하나가 실패해도 한자 목록과 퀴즈까지 사용할 수 없어진다.

- 한자 목록과 퀴즈는 한자 데이터만 정상이라면 사용할 수 있게 하라.
- 읽기 페이지는 읽기 데이터와, 본문 속 한자 링크·팝오버에 필요한 한자 인덱스를 올바르게 준비해야 한다.
- 불필요한 요청을 줄이되, 읽기 페이지에 필요한 한자 인덱스까지 제거하지 마라.
- 페이지 진입과 같은 문서 내 섹션 이동 모두에서 필요한 데이터가 준비되도록 하라.
- 실패한 Promise가 캐시에 남아 재시도가 계속 실패하지 않게 하라.
- 진행 중 요청을 재사용하거나 중복 요청을 막을 경우에도, 실패 후 재시도는 실제로 다시 동작해야 한다.

### 3-2. 활성 화면에서 보이는 오류와 재시도

현재 공통 오류 안내가 한자 화면 내부에만 표시되어 읽기·퀴즈 페이지에서는 오류 메시지와 재시도 버튼이 보이지 않는다.

- 활성 페이지에서 로딩·성공·실패 상태를 명확히 표시하라.
- 실패한 화면에서 오류 설명과 재시도 버튼에 접근할 수 있어야 한다.
- 재시도 성공 시 오류 상태를 제거하고 정상 화면으로 복구하라.
- 한 데이터의 실패가 관련 없는 정상 화면까지 실패 상태로 바꾸지 않게 하라.
- 오류 UI를 추가할 때 기존 디자인과 문구 톤을 유지하라.
- 재시도 과정에서 이벤트 핸들러나 필터 옵션이 중복 등록되지 않아야 한다.

### 3-3. 숨겨진 한자 목록의 불필요한 렌더링 제거

리뷰 당시 읽기·퀴즈 첫 진입에서도 화면에 보이지 않는 한자 카드 96개와 관련 DOM이 생성됐다.

- 읽기·퀴즈 첫 진입에서 숨겨진 한자 목록 카드를 미리 만들지 마라.
- 필요한 데이터와 인덱스 준비, 실제 카드 DOM 렌더링을 구분하라.
- 한자 섹션에 진입할 때 필요한 목록을 정상적으로 초기화하라.
- 상세 화면의 학년·JLPT 링크, 한자 링크, 유효한 해시, 브라우저 뒤로/앞으로 이동을 보존하라.
- 함수 호출만 삭제해 다른 이동 경로를 깨뜨리지 마라.

## 4. 필터·URL·브라우저 탐색 상태의 일관성

주요 파일: `src/main.js`.

### 4-1. 기존 학년·JLPT URL 상태 동기화

재현 사례:

1. JLPT N5 링크로 들어가면 URL에 `?jlpt=JLPT+N5`가 남는다.
2. 초기화 버튼을 누르면 화면은 전체 일반 한자로 돌아간다.
3. 새로고침하면 URL의 N5 조건이 다시 적용된다.

요구사항:

- 기존에 지원하는 `grade`, `jlpt` 쿼리와 실제 필터 상태를 일치시켜라.
- 최초 진입, 필터 직접 변경, 상세 화면의 학년·JLPT 링크, 초기화, `popstate`를 함께 처리하라.
- `pushState`와 `replaceState`의 사용 기준을 일관되게 정하고, 불필요하게 브라우저 히스토리를 늘리지 마라.
- 초기화하면 검색어·학년·JLPT·정렬과 획수/음 선택 상태가 서비스의 기본 상태로 돌아가야 한다.
- 초기화 이후 새로고침해도 지운 조건이 다시 살아나지 않아야 한다.
- 초기화로 취소한 선택이나 상세 화면을 다시 여는 앱 소유의 한자 해시가 있다면 함께 정리하라.
- 앱이 소유하지 않은 쿼리 파라미터나 관련 없는 해시는 보존하라.
- 이번 작업에서 검색어와 정렬까지 모두 URL로 직렬화하는 새 기능을 만들 필요는 없다.
- 지원하지 않는 쿼리 값으로 화면 전체가 실패하지 않게 하라.

### 4-2. 결과가 없는 활성 획수·음 선택을 해제할 수 있게 유지

재현 사례:

1. 획순 정렬에서 1획을 선택한다.
2. `犬`를 검색한다.
3. 결과가 0개가 되고 1획 선택은 내부에 남지만, 인덱스에는 4획만 표시된다.

요구사항:

- 검색이나 다른 조건 변경으로 결과가 없어져도 현재 선택된 획수·음 버튼을 인덱스에서 유지하라.
- 선택 상태를 사용자가 알아볼 수 있어야 하고, 해당 버튼을 다시 눌러 해제할 수 있어야 한다.
- 검색 결과에 포함되는 다른 획수·음과 활성 선택을 중복 없이 합쳐 표시하라.
- 사용자에게 알리지 않고 활성 선택을 자동으로 바꾸지 마라.
- 위 사례에서 1획 선택을 해제하면 `犬`가 정상적으로 나타나야 한다.
- 음 기준 정렬에도 같은 원칙을 적용하라.

## 5. 모달과 팝오버의 접근성·닫기 순서

주요 파일: `src/main.js`, `src/study.html`, `src/styles.css`.

### 5-1. 실제 포커스 제한과 복원

현재 사용자 정의 모달에 `aria-modal="true"`가 있지만, Shift+Tab으로 배경의 개인정보·분석 설정 버튼 등에 포커스가 이동할 수 있다.

- 상세 모달과 이미지 모달이 열리면 포커스가 활성 모달 안으로 이동해야 한다.
- Tab과 Shift+Tab으로 포커스를 이동할 때 활성 모달 내부에서 순환해야 한다.
- 모달 뒤의 페이지는 키보드와 보조 기술 관점에서 적절히 비활성화되어야 한다.
- 닫을 때는 모달을 연 요소로 포커스를 복원하라.
- 원래 요소가 사라졌거나 더 이상 포커스를 받을 수 없다면 적절한 대체 위치로 복원하라.
- 포커스 가능한 요소가 없을 때도 안전하게 동작해야 한다.
- 현재 구조를 보완하거나 네이티브 `<dialog>`를 사용할 수 있다. 특정 구현 방식을 강제하지 않는다.
- 배경을 `inert` 처리하거나 네이티브 모달을 도입할 경우, body에 별도로 붙는 한자 팝오버가 함께 막히지 않게 하라.
- 스크롤 잠금도 실제로 열린 모달 상태와 일치시켜라.

### 5-2. 가장 위에 열린 요소부터 닫기

현재 상세 모달에서 한자 팝오버를 연 뒤 Escape를 누르면 부모 상세 모달이 먼저 닫히고 팝오버가 남을 수 있다.

- Escape는 가장 위에 활성화된 팝오버나 모달을 먼저 닫아야 한다.
- 상세 모달 안의 한자 팝오버가 열려 있다면 첫 Escape는 팝오버만 닫고 상세 모달은 유지하라.
- 부모 모달을 닫으면 그 모달에 속한 팝오버와 임시 상태도 함께 정리하라.
- 제거된 DOM 요소를 팝오버의 anchor로 계속 참조하지 마라.
- 이미지 모달을 닫으면 아래 상세 모달의 포커스와 스크롤 잠금 상태가 올바르게 복원되어야 한다.
- 닫기 버튼, 배경 클릭, Escape, 이전 한자 복귀, 브라우저 뒤로 이동에서 일관된 정리를 수행하라.
- 한 번의 키 입력으로 의도하지 않은 여러 계층을 동시에 닫지 마라.

ARIA 속성만 바꾸고 완료 처리하지 말고 실제 브라우저에서 Tab·Shift+Tab·Escape를 검증하라.

## 6. 퀴즈 시작 실패 시 이전 결과 제거

주요 파일: `src/main.js`.

재현 사례:

1. 정상 조건에서 퀴즈를 끝내 결과 화면을 연다.
2. 설정으로 돌아간다.
3. 선택 가능한 한자가 4개 미만인 조건으로 시작한다.
4. 새 오류 안내와 이전 퀴즈 결과·다시 시작 버튼이 함께 남는다.

요구사항:

- 새 퀴즈 시작 전에 이전 문제·점수·결과·진행 상태를 일관되게 초기화하라.
- 유효한 퀴즈를 만들 수 없으면 설정 화면에서 이유를 표시하고 조건을 수정할 수 있게 하라.
- 이 경우 이전 결과와 완료 메시지, 이전 조건의 다시 시작 버튼이 노출되어서는 안 된다.
- 유효한 조건으로 바꾸어 다시 시작하면 정상 퀴즈로 복구되어야 한다.
- 4지선다를 만들기 위한 최소 후보 수와 사용자가 요청한 문제 수를 구분하라.
- 후보가 4개 이상이면 요청 문제 수가 10개라는 이유만으로 무조건 거부하지 마라. 현재 서비스의 문제 수 조정 동작을 유지하라.
- 정답과 보기 생성, 문제 진행, 결과 집계의 기존 정상 동작을 보존하라.

## 7. 잘못된 한자 해시와 초기화 중복 방지

주요 파일: `src/main.js`.

### 7-1. 해시 파싱 오류를 데이터 오류와 분리

재현 사례: 새 페이지로 `/kanji/#kanji=%`에 직접 접속하면 `decodeURIComponent`가 실패하고, 정상적으로 받아온 한자 데이터까지 로딩 실패로 처리된다.

- 한자 해시의 URI 디코딩을 안전하게 처리하라.
- 잘못된 해시는 무시하거나 해당 앱 소유 해시만 정리하고, 정상 한자 목록을 계속 보여라.
- 해시 해석 실패를 데이터 다운로드·파싱 실패로 취급하지 마라.
- 유효한 `#kanji=...` 링크는 계속 상세 화면을 열어야 한다.
- 형식은 유효하지만 데이터에 없는 한자를 가리키는 해시도 화면 전체를 실패시키지 않아야 한다.
- 같은 문서의 해시 변경뿐 아니라 새 페이지로 직접 진입하는 경우를 테스트하라.

### 7-2. 초기화와 재시도를 멱등적으로 처리

현재 오류 후 재시도하면 학년 선택 옵션이 11개에서 21개로 늘어나는 등 중복 생성이 발생할 수 있다.

- 필터 옵션을 다시 구성해도 개수가 증가하지 않게 하라.
- 이벤트 리스너, 인덱스, 카드, 관찰자 등이 재시도 횟수에 따라 누적되지 않게 하라.
- 필요한 초기화는 한 번만 수행하거나, 재실행해도 동일한 결과가 되도록 하라.
- 여러 번 실패한 뒤 성공해도 정상 최초 진입과 같은 상태가 되어야 한다.
- 실제 데이터 실패의 재시도 기능을 제거하는 방식으로 해결하지 마라.

| 읽기 데이터 19→1 급감 또는 기존 ID 삭제·교체 | 기본 모드에서 실패하고 기존 데이터가 보존된다. |
| 읽기 분류 오타·객체 본문·비어 있거나 잘못된 버전 | 구체적인 스키마 오류로 실패한다. |
| 이전 파일 부재와 이전 파일 손상 | 최초 생성과 손상을 구분하며, 손상은 조용히 덮어쓰지 않는다. |
| 한쪽 데이터 검증 실패 또는 파일 교체 중 실패 | 한자·읽기 두 파일 모두 이전의 일관된 상태를 유지한다. |

현재 데이터의 개수에 종속된 테스트는 fixture에서 기대값을 계산하거나 해당 테스트의 전제임을 명확히 하라. 운영 코드에 리뷰 당시 수치를 고정해 넣지 마라.

브라우저 회귀 테스트 도구가 없다면 필요한 최소 설정을 추가하라. 테스트가 저장소에서 재현되도록 하고, 특정 개발 환경의 브라우저 절대 경로나 개인 디렉터리에 의존하지 마라.

모달 접근성은 DOM 속성 확인만으로 대체하지 마라. 실제 브라우저에서 키보드 이동과 닫기 순서를 검증하라. 외부 네트워크나 이미지·폰트·분석 서비스가 필요한 부분은 적절히 분리하거나 mock 처리하고, 그 제한을 보고하라.

### 11-3. 명령과 CI

- `package.json`에 다른 개발자가 실행할 수 있는 명확한 테스트 명령을 제공하라.
- 깨끗한 의존성 설치를 확인하고, 관련 테스트와 `npm run build`를 실행하라.
- 빌드 결과의 주요 페이지 경로가 계속 생성되는지 확인하라.
- 기존 CI가 있으면 해당 검증을 통합하라.
- CI가 없다면 `npm ci`, 관련 테스트, 빌드를 실행하는 최소 GitHub Actions 구성을 추가하라.
- CI에 운영 Sheets 접근이나 비밀 값이 필요하지 않게 하라.
- 브라우저 테스트를 추가한다면 CI에서 필요한 브라우저 설치 단계도 재현 가능하게 구성하라.
- 테스트 실패를 통과시키려고 기존 검증을 약화시키거나 중요한 사례를 삭제하지 마라.
- 남은 구체적 위험을 확인한 뒤에는 무관한 리팩터링이나 테스트 범위를 계속 늘리지 말고 작업을 마무리하라.

## 12. 완료 기준과 최종 보고

### 완료 기준

1. 현재 코드에서 존재하는 이번 명세의 결함을 수정했거나, 이미 해결된 항목임을 근거와 함께 확인했다.
2. 정상 학습 데이터가 계속 로드되고, 잘못된 동기화 응답이 기존 두 파일을 손상시키지 않는다.
3. 한자·읽기·퀴즈의 데이터 의존성, 오류 표시, 재시도가 각 화면에서 정상 동작한다.
4. URL·필터·해시·브라우저 탐색 상태가 일관되고, 반복 초기화에 따른 중복이 없다.
5. 모달 포커스와 닫기 순서, 퀴즈 시작 실패 상태가 실제 브라우저에서 검증되었다.
6. 명시한 학습 데이터 3건 외에 의도하지 않은 콘텐츠 변경이 없다.
7. 의존성 패치, 문서, 관련 테스트와 빌드가 확인되었다.
8. 기존 디자인과 공개 경로를 유지하며, 검토 가능한 로컬 diff가 남아 있다.

### 최종 응답에 포함할 내용

- 변경한 파일과 각 변경의 목적.
- 명세 항목별 완료·이미 해결됨·미완료 상태와 근거.
- 실행한 명령, 테스트 결과와 빌드 결과.
- 실제 브라우저로 확인한 주요 동작과 재현 결과.
- 학습 데이터 diff의 범위와 Google Sheets 원본에 필요한 후속 교정.
- 남은 제한, 실행하지 못한 검증, 별도로 남긴 콘텐츠·SEO·이미지 호스팅 과제.

실행하지 않은 테스트를 통과했다고 쓰지 마라. 환경 제약이 있으면 실제로 확인한 범위와 확인하지 못한 범위를 구분하라. 별도 요청이 없으면 커밋·push·배포는 수행하지 말고 로컬 변경 상태로 마무리하라.
